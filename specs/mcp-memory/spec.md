# Personal memory over MCP

Status: phase 1 in progress (opened 2026-11-23).

## Goal

Any person can connect their own long-term memory to Mycellios Agent and
decide which Micos may use it. Micos know when they have that memory and use it
without being asked. Replacing the memory service does not change the Micos,
their tools or their permissions; only the connection behind them changes.

Mycellios contains no integration for a particular memory product. The only
channel is the Model Context Protocol (Streamable HTTP) with OAuth 2.1, plus
the open tool profile defined below. Jarvis, or any other memory, is just one
server that implements that profile.

## Non-goals

- A Jarvis-specific provider, tool name, header, token or setting anywhere in
  Mycellios.
- Hosting memories for users. Mycellios keeps its own local Mico memory
  (`MemoryDocument`, `MEMORY.md`); this spec only adds an external, user-owned
  memory.
- Automatic migration between memory services (see "Changing memory service").
- Making Jarvis multi-tenant. That is a Jarvis decision, tracked separately.

## Current state

- `SemanticMemoryProvider` (`src/agent/packages/adapter-kit/src/interfaces.ts`)
  has `recall`, `save`, `purgeHistory` and optional `forget`. The executor
  exposes `recall_memory`, `save_memory` and `forget_memory` through
  `selectMemoryTools` when a provider is configured.
- Providers are product-specific adapters (Supermemory, Honcho, Serenity) in
  `memory-provider-factory.ts`, configured with static credentials.
- `SpaceMemoryConfig` allows one provider per Space, set by the Space owner.
  When it exists, every Mico in the Space uses it; `Bot.memoryScope` only
  chooses `isolated` or `shared` namespaces. There is no per-Mico denial.
- Automatic recall runs only after a thread's history has been compacted
  (`executor.ts`, `includeSemanticRecall && historyCompactedUpToSeq != null`).
- Recalled facts are already framed as untrusted data
  (`formatRecalledMemory`, `history-compaction.ts`).
- The MCP client already implements OAuth 2.1 for remote servers
  (`mcp-oauth.ts`): protected-resource metadata (RFC 9728), authorization
  server discovery, dynamic client registration, PKCE, RFC 8707 resource
  binding and refresh. Per-Mico MCP grants already exist (`BotMcpServer`).

## Memory MCP profile v1

A remote MCP server qualifies as a memory server when `tools/list` contains the
required tools below with compatible input schemas. Mycellios publishes this
profile in its docs so any memory service can implement it.

| Tool | Required | Annotation | Input | Result (`structuredContent`, or JSON text) |
|---|---|---|---|---|
| `memory_search` | yes | `readOnlyHint: true` | `query` (string, 2..500), `limit` (int, 1..10), optional `projectId` (string) | `{ results: [{ id, title?, snippet, score?, updatedAt?, projectId?, source? }] }` |
| `memory_read` | yes | `readOnlyHint: true` | `id` (string), optional `offset`, `maxChars` (500..12000) | `{ id, title?, content, updatedAt?, nextOffset? }` |
| `memory_write` | no | `readOnlyHint: false` | `title` (1..200), `content` (1..8000 bytes), optional `projectId`, `tags[]`, `operationKey` | `{ id, status: "created" \| "updated" \| "unchanged" }` |
| `memory_forget` | no | `destructiveHint: true` | `id`, optional `reason` | `{ id, forgotten: boolean }` |
| `memory_status` | no | `readOnlyHint: true` | none | `{ writable?: boolean, projects?: [{ id, name }] }` |

Rules:

- Unknown result fields are ignored; missing required fields make the call fail
  closed for that turn (logged, never retried as another verb).
- `operationKey` is an idempotency key generated by Mycellios
  (`mycellios:<connectionId>:<runId>:<sha256(content)>`). Servers must scope it
  to the authorized connection so one client cannot overwrite another's entry.
- Write capability requires both the `memory_write` tool and an OAuth grant
  that allows it (scope advertised by the server, conventionally
  `memory.write`). Read-only servers stay fully usable.
- Optional adapter: a connection may store an explicit mapping from profile
  tools to differently named tools with the same semantics. This keeps the
  channel standard while allowing servers that predate the profile. The
  mapping is generic data, never a built-in vendor table.

## Connections

New table `MemoryConnection` (additive migration, Agent DB):

- `id`, `userId` (owner), `spaceId`, `name`, `endpoint` (HTTPS URL),
  `transport` = `streamable_http`, `status`
  (`connected` | `reconnect` | `disabled`), `capabilities`
  (`{ read: true, write: boolean, forget: boolean, projects: boolean }` from the
  last probe), `toolMapping` (nullable JSON), `secretId` (OAuth material, via
  the existing secret store), `createdAt`, `updatedAt`, `lastProbeAt`.
- A connection belongs to one person. Other Space members cannot see its
  endpoint, projects or contents and cannot grant it.
- Connecting: the user pastes the URL; Mycellios runs the existing MCP OAuth
  flow (discovery, dynamic registration, PKCE, resource binding), requesting
  read scope and, only if the user ticks "allow writing", the write scope. Then
  it probes `tools/list` and `memory_status` and records capabilities.
- Static bearer tokens are accepted only for servers that publish no OAuth
  metadata, and are stored like other MCP secrets.
- Private/LAN/loopback endpoints keep the existing rule: refused unless the
  deployment owner sets `mcpAllowPrivateEndpoint`. Desktop and self-hosted
  installs may set it; the hosted service does not.
- Revoking deletes the stored tokens and removes every grant of that connection.
  Calling the server's revocation endpoint when advertised is pending (the
  shared MCP OAuth broker does not do it yet).
- A person may have several connections (for example the old and new service
  during a change).

`SpaceMemoryConfig` and its three adapters remain as a legacy Space-level
provider until phase 4.

## Grants per Mico

New table `MicoMemoryGrant`: `id`, `botId`, `connectionId`, `access`
(`read` | `read_write`), `allowForget` (boolean), `projectIds` (string[],
empty = whole memory the token allows), `autoRecall` (boolean, default true),
`createdAt`, `updatedAt`, `grantedByUserId`.

- **Default is no access.** Connecting a memory grants nothing. Each Mico is
  enabled explicitly from the Mico's settings or from the connection's page.
- `read_write` is offered only when the connection has write capability.
  `allowForget` requires `read_write` and the server's `memory_forget` tool.
- Only a person changes grants, through the authenticated UI/API. Micos,
  routines, delegated runs, peer messages and messaging channels can never
  create, widen or remove a grant.
- Only the connection owner can grant it, and only to Micos they can manage.

## Runtime behavior

For each run the executor resolves the Mico's grants, then filters them:

1. **Acting user.** A personal memory is used only when the run acts for the
   connection owner (`run.userId === connection.userId`), including the
   owner's routines and follow-ups. Runs started by other Space members,
   public links, event guests or external messaging senders get no access to
   it. (Explicit sharing with other members is an open question, not v1.)
2. **Channel class.** Messaging-channel runs (WhatsApp, Telegram, Slack…) and
   group threads get no external memory unless the grant later adds an explicit
   channel opt-in. Nothing is ever written from a direct message received on a
   messaging channel.
3. **Connection health.** `reconnect` or `disabled` connections are skipped; the
   Mico is told memory is temporarily unavailable rather than silently losing
   it.

With at least one usable grant:

- **Automatic recall every turn**, not only after compaction: one
  `memory_search` per usable connection with the user's message as query,
  `limit` ≤ 5 per connection, filtered by `projectIds`, merged and capped at
  8 KB of formatted text. Total recall budget is 2.5 s; slow connections are
  skipped for that turn. Results use the existing untrusted framing
  (`formatRecalledMemory`) with the connection name as provenance.
- **Tools.** The existing `recall_memory`, `save_memory` and `forget_memory`
  names are kept so the Mico's tools do not change with the provider.
  `recall_memory` searches all usable connections and can read a full entry by
  id (`memory_read`). `save_memory` appears only with a `read_write` grant and
  writes to the single connection marked as the Mico's write target.
  `forget_memory` appears only with `allowForget` and always shows an approval
  card before calling the server.
- **Instructions.** The run's system context states which memories the Mico
  has (by connection name and access level), that it should consult them
  before durable decisions, save only durable facts the user would want kept,
  and treat recalled text as evidence, never instructions. A Mico without
  grants receives neither the tools nor this text.
- **Secrets and content.** `save_memory` content passes the existing run-secret
  redaction first and is refused if it still matches a secret pattern.
  Contents are never logged; audit events record connection id, tool, result
  ids and sizes only.
- **Bounds.** 10 s per call, 64 KB response cap, no redirects to another
  origin, one MCP session per call terminated afterwards (as Serenity does
  today), and a per-connection limit of 60 calls per minute.

## Changing memory service

- Grants reference a connection, so a person can switch services by connecting
  the new one, choosing "replace" on the old connection, and Mycellios moves
  every grant (access, projects, autoRecall) to the new connection in one
  transaction. The Micos keep the same tools and instructions.
- Memories already stored stay in the old service. Supported options:
  - keep the old connection granted read-only during the transition (recall
    merges both);
  - an optional, user-started copy job later (search/read from the old,
    `memory_write` to the new, idempotent by `operationKey`). Not in v1.

## Phases

1. **Profile and connections.** Publish the profile doc
   (`src/agent/docs/memory-mcp.md`), add `MemoryConnection`, the
   `memory.connections` list/create/check/remove API and the Personal memory
   settings section. Each connection is a personal `McpServer` row, so it reuses
   the existing transport, OAuth broker and endpoint checks; those rows are hidden
   from the generic MCP list and refused as Mico tool assignments. No runtime use
   yet.
2. **Grants and read-only runtime.** `MicoMemoryGrant`, Mico settings UI,
   per-run filtering, automatic recall every turn, `recall_memory`, system
   context. Qualify against a real profile server (Jarvis `/api/v1/mcp/memory`)
   and against a local test server in the testkit.
3. **Writes and forget.** `save_memory`/`forget_memory` with write scope,
   redaction, approval card and idempotency.
4. **Legacy.** Decide whether Supermemory/Honcho/Serenity become profile
   servers or stay as legacy Space providers; no removal without a migration
   path for existing Spaces.

Each phase is its own PR, with `src/agent/changelog.d` notes.

## Security checklist

- No vendor-specific code paths; CI test asserts the memory connector contains
  no product names.
- OAuth only from server-published metadata; resource binding enforced;
  tokens encrypted in the secret store and never sent to the model.
- Per-Mico default-deny; per-run acting-user check; no access from messaging,
  public, guest or delegated contexts.
- Recalled content always untrusted, bounded and escaped.
- Writes redacted and idempotent; forget requires human approval.
- Private endpoints only with deployment-owner authorization.

## Verification

- Contract tests for the profile parser (required tools, schemas, mapping).
- Executor tests: no grant → no tools and no recall; read grant → recall and
  `recall_memory` only; other member's run → no access; messaging run → no
  access; reconnect status → unavailable notice; recall budget timeout.
- OAuth tests reuse the `mcp-oauth` suite with a fake authorization server.
- PostgreSQL test for the additive migration and grant replacement transaction.
- Manual qualification: connect Jarvis `/api/v1/mcp/memory`, grant one Mico,
  confirm another Mico has no access, revoke and confirm access ends.

## Open questions

- Should an owner be able to share a memory grant with other Space members'
  runs, and with what audit?
- Should automatic recall be skipped for very short messages to save latency?
- Jarvis side (separate repo): `memory.write` scope and `memory_write` tool,
  semantic search on `/mcp/memory`, restricted CORS, org filter on deprecate,
  body limits, and multi-user only if offered as a service.
